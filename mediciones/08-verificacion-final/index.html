Verificación final¶

Corrida del 2026-11-09 sobre un clon limpio del commit 3bca905, en la misma computadora de la medición de tiempo de respuesta. Después de esa corrida cambiaron documentos, la forma de apuntar a Neon, que se probó aparte (docker compose up, la prueba de humo y Postman en la copia local, y run-on-neon.sh con lecturas), y el paquete de cada clase, con todos los pasos repetidos sobre otro clon limpio (abajo). Por último se agregó el control de posibles duplicados, otra vez con todos los pasos sobre un clon limpio (abajo), y se ajustó el tablero de Grafana, sin cambios en el código de la API (abajo). Antes de entregar se repitieron los pasos desde un clon de main (al final). GitHub Actions está bloqueado en esta cuenta (RFC, sección 11.2): estos son los pasos de .github/workflows/ci.yml, corridos en local, más los ejemplos del README y la medición con volumen. Lo que encontró la verificación, antes de este clon. Todo corregido, y con su test donde hay código:

Quién la encontró Qué pasaba Qué se hizo

Con el tablero ajustado (2026-11-11)¶

El tablero de Grafana pasó de cinco a seis paneles. Los errores se separaron en errores del servidor (5xx) y del cliente (4xx), los cuatro paneles que cuentan pasaron a leer el contador desde que arrancó la API, y cada panel sumó su explicación (RFC, sección 8.3). No cambió el código de la API ni sus tests: cambió observability/grafana/dashboards/cocos-api.json. Se probó en un segundo docker compose, con otros puertos y el mismo archivo, para poder reiniciar la API y provocar errores.

Con el archivo final, sobre un up nuevo:

Con el panel anterior, un error que pasaba una sola vez no se veía: después de la colección de Postman, su consulta no devolvía nada para el 422.

Lo que apareció al probar, antes de dar por bueno el archivo:

Qué pasaba Qué se hizo
Los paneles de órdenes y de rechazos quedaban vacíos si la colección de Postman se corría apenas levantaba todo: las tres veces que se probó, con 4 órdenes grabadas. Contaban con increase(), que no ve lo que pasa antes de la primera lectura de Prometheus, y esa lectura llegó entre 3,6 y 10,5 segundos después de que la API estuvo lista (cuatro corridas). Ya pasaba con el tablero anterior. Con la prueba de humo antes, no, porque espera esa lectura los cuatro paneles que cuentan leen el contador desde que arrancó la API
Con un solo tipo de error, su barra salía sin nombre. También pasaba en el panel de órdenes, con una sola combinación cada barra lleva su nombre
El nombre largo de la cancelación se cortaba y tapaba el código el código va primero: 409 · POST /users/…
Con la API detenida, los errores del servidor mostraban un 0 en verde el 0 se muestra solo si Prometheus está leyendo la API
Un ícono azul de aviso en el panel de latencia, una vez, con muchos pedidos justo después de reiniciar la API es un aviso informativo de Prometheus, que corrige solo una diferencia mínima. Quedó en el runbook

La captura del portal (métricas) es de ese segundo compose, con los diez minutos de tráfico de ejemplo.
